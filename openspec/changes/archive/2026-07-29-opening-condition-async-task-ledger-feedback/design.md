## Context

The opening-condition platform already has platform-owned task facts, events, packet intake, matching, human review, and report state. The current `trial-bootstrap` path creates/publishes basis and master data, initializes the task, then immediately runs checklist matching before responding. That makes the UI feel synchronous: a user can click "start parsing" and wait without seeing the new history row.

The next production-focused step is to make task ownership visible as soon as the platform has enough facts to create the run. The actual matching logic can remain deterministic and local for now; this change only changes the timing and refresh behavior.

## Goals / Non-Goals

**Goals:**

- Return a persisted task immediately after bootstrap intake succeeds.
- Continue matching after the response and store the resulting task/events in the existing pilot store.
- Make the agent console select and display the newly created run immediately.
- Refresh selected task state while the task is in an active workflow state.
- Keep previous run history and unique run ids intact.

**Non-Goals:**

- No new worker framework, durable queue, Redis, database migration, or provider job orchestration.
- No deep PDF page splitting, OCR marking, or legal rectification generation.
- No frontend direct calls to MaxKB/OCR providers.
- No changes to the construction-plan review platform.

## Decisions

- Use an explicit async flag on `trial-bootstrap` rather than changing the existing synchronous behavior globally. Existing tests and advanced pages can continue using the synchronous contract.
- Implement the background continuation in the Node BFF with a bounded in-process job registry. This is intentionally MVP-grade and recoverable by explicit `/match` if the process restarts.
- Use existing task events and state labels for progress. The frontend shall poll selected active runs instead of inventing frontend-only workflow facts.
- Keep the task id generated by the UI run-id helper. The backend still normalizes it and upserts by id, so history isolation depends on using a fresh id for each upload.

## Risks / Trade-offs

- In-process background jobs do not survive server restart -> mitigate by returning the persisted `packet_uploaded` task and allowing manual/refresh-driven continuation later.
- A matching failure after the initial response could be missed by the initial UI event -> mitigate by refreshing the selected task and recording `task.failed` events.
- Upload itself is still synchronous before task creation -> acceptable for this slice because object storage must return stable object refs before platform task intake.
